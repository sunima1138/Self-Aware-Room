## 1. Purpose

This document defines the implementation-facing class and object model for the SAR computational pipeline. It translates architectural responsibilities into interface contracts, component boundaries, and lifecycle expectations for software development.

### 1.1 Scope

The scope includes base interfaces, object-flow ownership, extension points, and layer interaction patterns. It does not lock implementation to a single framework, inheritance strategy, or runtime engine.

### 1.2 Relationship to Pipeline Specification

The generalized pipeline specification defines architectural boundaries and data-flow intent. This document defines how software components can implement those boundaries as classes, interfaces, or protocols.

## 2. Design Principles

The class and object model should preserve architectural boundaries while allowing pragmatic implementation choices.

### 2.1 Interface-First Boundaries

Each computational stage should expose a clear interface contract. Concrete classes may vary, but interface behavior must remain consistent across implementations.

### 2.2 Composition over Deep Inheritance

Composition should be preferred over deep inheritance hierarchies. Shared base types are allowed when they reduce duplication without hiding layer responsibilities.

### 2.3 Traceability by Construction

Classes should emit or preserve trace metadata as part of normal operation, not as optional add-ons.

## 3. Core Component Types

This section defines implementation-level component categories that map to architectural layers and cross-cutting functions.

### 3.1 Pipeline Stage Component

A pipeline stage component processes input objects and emits output objects according to a stage contract.

Suggested interface responsibilities:

- accept input objects,
- validate preconditions,
- execute stage transformation,
- emit output objects,
- emit stage-level diagnostics and status.

### 3.2 Cross-Cutting Observer Component

A cross-cutting observer component records traces, timing, uncertainty, and outcomes across all stages.

Suggested interface responsibilities:

- receive stage telemetry and trace events,
- persist or forward observability records,
- provide replay and evaluation hooks,
- expose diagnostics for development and operations.

### 3.3 Contract Objects

Contract objects represent data exchanged between components and should be versioned and validated.

Core object categories:

- observation,
- event,
- entity,
- state,
- semantic_state,
- decision,
- intent,
- execution_plan,
- dispatch,
- evaluation_record.

### 3.4 Distinction Between Contract Objects and Components

Contract objects are data artifacts that move between stages. They carry identity, provenance, timing, quality, and payload fields defined by the shared object contract.

Pipeline stage components, policy components, orchestration components, dispatch adapters, and O1 observers are processing classes, not transport artifacts. They should implement stage interfaces and emit contract objects, but should not be modeled as contract objects themselves.

Component runtime metadata (for example, component name, version, configuration version, host/node identity, startup time, heartbeat, and latency) should be handled as operational telemetry and then attached to emitted contract-object provenance where required.

## 4. Object-to-Component Mapping

This section maps object creation and transformation to implementation component categories.

### 4.1 Stage Mapping

- L0 edge capture components emit transport frames and raw capture payloads.
- L1 ingest acquisition components map edge frames to source-local observation objects and persist raw evidence by reference.
- Normalization components transform observations into canonical observations.
- Coherence components transform observations into event/entity/state objects.
- Semantic components transform state into semantic_state objects.
- Policy components transform semantic_state into decision/intent objects.
- Orchestration components transform intent into execution_plan objects.
- Dispatch components transform execution_plan into dispatch/result records.
- O1 components record and evaluate trace relationships across all transformations.

### 4.2 Ownership and Mutability

Each stage should define whether it mutates incoming objects, wraps them, or emits new immutable objects. The chosen pattern must preserve provenance and avoid ambiguous state transitions.

### 4.3 Object Identity and Timestamp Assignment

Implementation components should follow a consistent identity and timing policy.

- L1 should preserve source-native IDs when present and assign UUIDv7 `object_id` values when native IDs are absent.
- L0 edge transport frames may use lightweight frame identifiers; canonical SAR `object_id` assignment occurs at L1 ingest when full observations are emitted.
- Each layer that creates a derived object should assign a new `object_id` and preserve parent linkage through provenance fields.
- Components should carry source capture and ingest/processing timestamps as separate fields.
- Multi-device components should expose clock quality metadata when available (for example, `clock_offset_estimate`, `clock_quality`, `sync_source`).
- Duplicate ID detection should emit a structured anomaly report to O1.

## 5. Lifecycle and Runtime Behavior

This section defines lifecycle expectations for implementation components.

### 5.1 Initialization

Components should declare required dependencies and configuration at initialization time. Missing required dependencies should produce explicit startup failures.

### 5.2 Processing Loop

Stages may run synchronously, asynchronously, or in event-driven mode, but they must preserve contract boundaries and traceability.

### 5.3 Degraded and Failure States

Each component should emit explicit degraded and failure states consistent with the pipeline specification.

### 5.4 Communication Record and Storage Hooks

Implementations should separate observability records from optional raw payload storage.

- O1 records should always capture transformation and decision traces.
- Large raw payloads should be referenced by pointer/URI and checksum rather than embedded in all log records.
- Retention and replay policy should be configurable by environment (prototype vs production).

## 6. Extension Model

This section defines how new modalities or outputs can be added without architectural breakage.

### 6.1 New Input Modalities

New input modalities should integrate by implementing acquisition and normalization contracts first, then joining coherence and integration pathways.

Modality rules should be defined as interface profiles over a shared transport contract rather than deep subclass hierarchies. For example, the audio streaming profile in D01.02 defines required audio fields and timing policy while preserving a common edge frame interface for other modalities.

### 6.2 New Output Channels

New output channels should integrate by implementing dispatch adapters under orchestration constraints.
