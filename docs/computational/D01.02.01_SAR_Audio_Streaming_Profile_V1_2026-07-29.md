# SAR Audio Streaming Profile

Document ID: D01.02.01  
Document Class: Modality Contract Profile  
Project: Self-Aware-Room (SAR)  
Status: Version 1 draft  
Date: 2026-07-29

## 1. Purpose

This document defines the audio modality profile layered on top of the shared streaming contract.

It specifies additional audio-required fields, metadata, retention behavior, and conformance checks.

## 2. Contract Position

This profile applies when modality is audio.

- Base contract: D01.02 Shared Streaming Contract.
- Audio profile: this document.

## 3. Normative Terms

The keywords MUST, SHOULD, and MAY are normative.

## 4. Audio Required Fields

### 4.0 Audio Frame Definition

For this profile, an audio frame is one ordered transport unit containing a bounded segment of audio data or a reference to persisted raw audio content.

Audio frame semantics:

- For streaming capture, a frame typically represents a short contiguous sample window.
- For package-style intake, a frame MAY represent a file-derived segment descriptor rather than inline samples.
- frame_index MUST be monotonic within a given source stream/session.

Implementations MAY choose frame duration and payload size based on latency, bandwidth, and processing constraints, provided ordering and timing policy remain conformant with D01.02.

### 4.2 Frame Versus Segment Semantics

This profile distinguishes transport framing from downstream analysis segmentation.

- Frame: ingest transport unit used for source ordering, timing, and payload carriage.
- Segment: derived analysis unit that MAY span one or more frames and MAY have variable duration.

Normative rules:

- L0/L1 transport conformance applies to frames, not to downstream semantic segmentation boundaries.
- Downstream components MAY derive segment objects for speech, phrase, event, or calibration workflows.
- If a derived segment spans multiple frames, implementations MUST preserve provenance linking the segment to source frame indices or source frame IDs.

When modality is audio, the following fields MUST be present on the frame or payload contract surface:

- encoding
- sample_rate_hz
- sample_format or bit_depth
- channel_count
- frame_index
- audio payload content (raw chunk bytes/samples or raw reference fragment)

Recommended optional fields:

- sample_format (for example, pcm_s16le, float32)
- bit_depth (required when sample_format does not fully encode numeric precision)
- nominal_bitrate_bps
- adc_full_scale_reference
- preamp_gain_db
- transport_crc

### 4.1 Encoding, Sample Format, and Bitrate Policy

Audio ingestion MUST provide enough information to unambiguously interpret time resolution and amplitude resolution.

Normative rules:

- sample_rate_hz MUST be provided.
- channel_count MUST be provided.
- encoding MUST be provided.
- sample_format or bit_depth MUST be provided.
- If encoding or sample_format is ambiguous with respect to numeric precision, bit_depth MUST be explicitly provided.

PCM handling guidance:

- For PCM streams, nominal bitrate MAY be derived from sample_rate_hz, bit_depth, and channel_count.
- Derived nominal bitrate formula:
	- nominal_bitrate_bps = sample_rate_hz x bit_depth x channel_count

Compressed stream handling guidance:

- For compressed transport (for example, Opus, AAC, MP3), nominal_bitrate_bps SHOULD be provided by the producer or ingest adapter.
- For variable bitrate streams, implementations MAY include both nominal_bitrate_bps and measured_effective_bitrate_bps over a defined window.

## 5. Audio Gating and Segmentation Metadata

For continuous operation, audio capture SHOULD support threshold-aware metadata so storage policy remains auditable.

Normative profile policy:

- If gating/segmentation policy is disabled, implementations MAY omit gating metadata fields.
- If gating/segmentation policy is enabled, implementations MUST provide the fields below on each relevant frame or segment descriptor:
	- gate_state (open or closed)
	- threshold_on_dbfs
	- threshold_off_dbfs
	- pre_roll_ms
	- post_roll_ms
	- dropped_by_policy
	- capture_policy
- If gating/segmentation policy is enabled, implementations SHOULD provide:
	- noise_floor_dbfs
	- rms_dbfs
- Implementations MAY provide additional tuning fields (for example, gate_confidence or noise_estimator_id) as long as required fields are preserved.

Where threshold_on_dbfs and threshold_off_dbfs are relative to the current estimated noise floor, hysteresis SHOULD be used to avoid gate chatter.

### 5.1 Room-Tone Discard Automation

Implementations MAY discard spans that never exceed the adaptive gate threshold above room tone.

If room-tone discard is enabled:

- the system MUST maintain a rolling pre-buffer (ring buffer) to avoid clipping event onset,
- the system SHOULD apply post-roll to preserve trailing context,
- the gate SHOULD use hysteresis (separate open and close thresholds),
- the payload SHOULD record gate decision metadata for audit and tuning.

Recommended starting values (deployment-tunable):

- pre_roll_ms: 300 to 800
- post_roll_ms: 500 to 1200
- threshold_on_dbfs: noise_floor_dbfs + 10
- threshold_off_dbfs: noise_floor_dbfs + 6

These values are relative offsets from current room-noise estimate, not universal absolute loudness thresholds.

### 5.2 Tentative Default Parameters

The following defaults are tentative starting points for implementation and testing.

They are not final acceptance thresholds and MUST be re-evaluated once live room experimentation begins.

| Parameter | Tentative Default | Notes |
| --- | --- | --- |
| pre_roll_ms | 500 | Preserve onset context before gate-open transition. |
| post_roll_ms | 800 | Preserve trailing context after gate-close transition. |
| threshold_on_offset_db | +10 dB over noise floor | Gate-open offset relative to adaptive room-tone estimate. |
| threshold_off_offset_db | +6 dB over noise floor | Gate-close offset relative to adaptive room-tone estimate. |
| default_source_latency_ms | 0.0 | Fallback when L0 does not provide latency estimate. |

## 6. Retention and Storage Modes

Implementations SHOULD expose a capture policy switch:

- full: retain all raw continuous audio within configured retention.
- hybrid: retain rolling continuous audio and durable event-linked segments.
- selective: retain event-linked segments and derived artifacts only.

In selective mode, implementations MAY delete raw audio after successful speech/event extraction, provided trace metadata and policy markers are retained.

Recommended retained markers in selective mode include:

- transcript or extracted artifact reference,
- extraction model/version,
- confidence/quality indicator,
- source frame/time interval,
- deletion_reason and retention_policy_id.

### 6.1 Low-Information and Noise-Floor Policy

This subsection defines handling for windows where no informative content exceeds policy thresholds.

Normative policy:

- Implementations MAY omit durable raw-audio storage for windows that remain below configured information thresholds.
- If raw audio is omitted for low-information windows, implementations MUST retain trace metadata sufficient for audit, including timing bounds and policy decision markers.
- Implementations SHOULD retain periodic baseline telemetry (for example, noise floor and RMS summaries) even when raw audio is not durably stored.
- If ambient regime changes are detected (for example, HVAC/compressor activation or sustained room-tone shift), implementations SHOULD persist a short baseline capture and updated noise-floor metadata for calibration continuity.

### 6.2 Speech and Phrase Spanning Policy

Speech and phrase boundaries are not required to align with ingest frame boundaries.

Normative policy:

- Implementations MAY derive phrase-level or utterance-level segments that span multiple frames.
- Segment-level artifacts used for ASR or semantic interpretation SHOULD include start/end timing and source frame linkage.
- Segment derivation MUST NOT rewrite original frame ordering or invalidate frame-level provenance.

## 7. Conformance Checklist

An audio L0/L1 path is conformant when:

1. Base D01.02 required fields are present.
2. Audio-required fields in Section 4 are present for modality audio.
3. Encoding/sample-format/bit-depth rules in Section 4.1 are satisfied.
4. L1 applies ingest-time and identity policy from D01.02.
5. Raw artifacts are retained according to configured storage mode with traceable references.
6. If room-tone discard is enabled, pre-buffer and gate decision metadata are present.
7. If gating/segmentation policy is enabled, required metadata fields in Section 5 are present.
8. If segment-level artifacts are produced, frame-to-segment provenance linkage is present per Sections 4.2 and 6.2.
