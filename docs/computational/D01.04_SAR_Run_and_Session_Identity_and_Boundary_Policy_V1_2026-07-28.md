# SAR Run and Session Identity and Boundary Policy

Document ID: D01.04  
Document Class: Shared Runtime Policy Specification  
Project: Self-Aware-Room (SAR)  
Status: Version 1 draft  
Date: 2026-07-28

## 1. Purpose

This document defines how SAR separates continuous sensing into manageable execution units without losing continuity.

It introduces `session_id` and `run_id` as distinct identifiers and defines boundary policy for always-on operation.

## 2. Core Model

### 2.1 session_id

`session_id` identifies a long-lived continuous operating context.

Examples:

- service uptime interval,
- operator shift interval,
- day-part capture interval.

### 2.2 run_id

`run_id` identifies one bounded pipeline execution window within a session.

One session contains many runs.

### 2.3 Relationship

- `session_id`: continuity boundary.
- `run_id`: processing and reporting boundary.
- multiple sensors MAY contribute to the same `run_id`.

## 3. Why Both IDs Are Required

Using only one identifier creates either ambiguity or fragmentation.

- only `session_id`: logs become too large and difficult to isolate per decision cycle,
- only `run_id`: continuity across long operation windows is lost.

Both IDs are required for reliable replay, reporting, and cross-stage traceability in continuous environments.

## 4. Boundary Policy for Continuous Activity

In constant-activity rooms, runs MUST be separated by deterministic policy, not silence detection.

Preferred baseline policy:

- fixed-duration run windows,
- optional overlap between adjacent runs,
- bounded run size by latency/throughput constraints.

### 4.1 Recommended Baseline (Tentative)

The following values are tentative and MUST be re-evaluated during live experimentation:

- run_window_seconds: 1 to 5 seconds,
- run_overlap_ms: 200 to 500 ms,
- max_objects_per_run: deployment-specific safety cap,
- max_run_latency_ms: deployment-specific service-level cap.

These are starting values, not final acceptance thresholds.

## 5. Identifier Generation Policy

- `run_id` SHOULD be generated at pipeline-run start.
- `session_id` SHOULD be generated at session start and reused across all runs in that session.
- both identifiers SHOULD use time-ordered UUIDv7 where available.

If UUIDv7 is not available in runtime, a documented fallback MAY be used temporarily.

## 6. Propagation Policy

For each log record and stage output, runtime should preserve enough identity metadata to group by run and session.

Minimum recommended propagation:

- O1 log record fields include `session_id` and `run_id`,
- stage-level status and transfer logs include `run_id`,
- artifact references (raw payload refs, derived outputs) are linked to `run_id`,
- object lineage remains in object-level provenance/trace fields.

## 7. Reporting Policy

Formatted reports SHOULD be generated per `run_id` from append-only JSONL logs.

Suggested report sections:

1. run header (`session_id`, `run_id`, start/end, host),
2. stage status timeline,
3. input/output counts by stage,
4. warnings/errors,
5. emitted artifacts and dispatch outputs.

## 8. Conformance Checklist

A runtime is conformant when:

1. each pipeline execution has exactly one `run_id`,
2. each run is associated with exactly one `session_id`,
3. all stage and pipeline logs can be grouped by `run_id`,
4. continuous activity can be segmented without requiring silence boundaries,
5. overlap policy is explicit and documented when used.
