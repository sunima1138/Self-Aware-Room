# SAR Computational Glossary

Document ID: D00.02  
Document Class: Baseline and Governance Reference  
Project: Self-Aware-Room (SAR)  
Status: Version 1 draft  
Date: 2026-07-29

## 1. Purpose

This glossary defines a controlled vocabulary for SAR computational documents and implementation artifacts.

It is intended to reduce terminology drift across architecture, contracts, implementation, and testing documents.

## 2. Scope

This glossary applies to terms used in the computational document set and the SAR core implementation.

When a term is defined differently in a subsystem-specific track, that track should reference this glossary and explicitly declare any scoped override.

## 3. Term Definitions

This section provides concise definitions for high-impact terms used throughout SAR computational specifications.

| Term | Definition | Primary Reference |
| --- | --- | --- |
| Base edge frame | Modality-agnostic L0 transport envelope containing required source identity and payload fields. | D01.02 |
| Canonical room entity | Singleton room Entity used as stable room context linkage across Event and State artifacts. | D02.01 and models.py |
| Coherence | Degree to which multiple observations can be treated as evidence of the same event, entity, or state. | D01.01 |
| Contract profile | Modality-specific extension of the shared streaming contract, expressed as conformance rules rather than inheritance. | D01.02.xx |
| Correlation | Cross-observation relationship identification process based on timing, location, feature patterns, and provenance. | D01.01 |
| DataObject | Abstract transport artifact base type for SAR pipeline objects, not a stage-processing component. | models.py |
| Decision | Policy-evaluated artifact describing whether and how system response should proceed. | D01.01 and models.py |
| Degraded status | Explicit stage outcome where processing continues with known limitations or reduced confidence. | stages.py and D01.01 |
| Dispatch | Channel-specific command artifact generated for output endpoint execution. | D01.01 and models.py |
| Edge observation frame | Lightweight transport frame emitted by source-adjacent capture nodes and mapped to Observation at ingest. | edge_ingress.py |
| Entity | Tracked subject or room-context artifact emitted by coherence/integration processing. | D01.01 and models.py |
| Evaluation record | O1 artifact capturing metrics, diagnostics, traces, and replay/evaluation outputs. | D01.01 and models.py |
| Event | Correlated occurrence hypothesis created from one or more observations after L3 integration. | D01.01 and models.py |
| Execution plan | Ordered and coordinated action artifact prepared by orchestration for dispatch. | D01.01 and models.py |
| Frame | Smallest ordered transport unit presented to ingest, defined generically in D01.02 and specialized by modality profiles. | D01.02 and D01.02.xx |
| Frame index | Monotonic source-local sequence value used to preserve ordering across frames within a source stream/session. | D01.02 |
| Identity backfill | L1 practice of preserving source-native identity while assigning canonical SAR object identity. | D01.02 |
| Indeterminate status | Explicit stage outcome where available evidence is insufficient for a reliable determination. | stages.py and D01.01 |
| Intent | Abstract request for system behavior emitted after policy evaluation and consumed by orchestration. | D01.01 and models.py |
| L0 | Edge capture and transport stage that frames and forwards source observations. | D01.01 |
| L1 | Ingest acquisition stage that stamps ingest timing, preserves source provenance, and emits observation artifacts. | D01.01 |
| L2 | Normalization and local abstraction stage that canonicalizes observation structure without cross-source reconciliation. | D01.01 |
| L3 | Coherence, correlation, and integration stage that emits event, entity, and state artifacts. | D01.01 |
| L4A | Semantic interpretation stage that converts coherent evidence into semantic state artifacts. | D01.01 |
| L4B | Policy and decision stage that evaluates semantics and emits decision and intent artifacts. | D01.01 |
| L5A | Orchestration stage that converts intent into prioritized execution plans. | D01.01 |
| L5B | Output dispatch stage that issues channel-specific commands and records dispatch outcomes. | D01.01 |
| Modality | Sensor or source class declared on ingress frames, such as audio, video, or motion. | D01.02 |
| O1 | Cross-cutting logging, replay, and evaluation plane observing all forward-processing layers. | D01.01 |
| Observation | Source-derived measurement or source-local frame artifact used as pipeline evidence. | D01.01 and models.py |
| Provenance | Lineage metadata linking artifacts to source-native identifiers, parent artifacts, and transformation context. | D01.02 and models.py |
| Room-state estimate | Bounded, confidence-weighted state output from L3 rather than absolute global truth. | D01.01 |
| Semantic state | Interpreted representation of system meaning emitted by L4A from coherent evidence. | D01.01 and models.py |
| Segment | Derived analysis unit that may span one or more transport frames and may have variable duration (for example phrase, utterance, or event window). | D01.02.01 |
| Shared streaming contract | Generalized contract defining required frame fields, timing policy, identity policy, and profile extension rules. | D01.02 |
| Stage component | Interface-first processing unit for a computational layer that accepts input artifacts and returns stage results. | stages.py |
| Stage result | Standard stage response wrapper containing output artifacts, stage status, and status messages. | stages.py |
| State | Bounded room or subsystem condition estimate emitted from coherence/integration processing. | D01.01 and models.py |
| Timestamp backfill | L1 policy deriving source capture time from receipt time and latency estimate when source time is absent. | D01.02 |

## 4. Governance Notes

This section defines how glossary terms should be maintained as the architecture evolves.

1. New normative terms should be added here when first introduced in a computational specification.
2. Any changes to existing definitions should include a brief note in the referencing document revision summary.
3. Terms that become obsolete should be retained with deprecation notes until dependent documents are updated.
